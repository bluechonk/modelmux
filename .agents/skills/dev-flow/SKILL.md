# dev-flow：探索式开发的收口流程

目标：把 dev 分支上累积的探索式提交（wip）整理成**可 PR 的主题分支**。
混乱是允许的 —— 收口时强制整理。

## 0. 心法（为什么这样做）

- **dev 是草稿纸**：探索期不要求想清楚，分支名可以先叫 `dev`，提交信息可以 `wip:` 开头。
- **commit 是存档点**：每完成一个能跑/能看的小片段就提交一次，为回退提供锚点。
- **整理会产出结构**：分支名、干净的历史、PR 内容，全是整理时的产出，不是开工前的输入。
- **一个 commit = 一个逻辑**：逻辑是整理出来的，不是憋出来的。与全局规则「版本控制」第 1 条同源。

## 1. 前置检查

```bash
git status                    # 工作树必须干净（脏改动先 wip 提交掉）
git log --oneline main..dev   # 列出本轮全部累积提交
git diff main..dev --stat     # 看这批提交动了哪些文件
```

- `dev` 不存在时先确认：当前是否就是探索状态？是，则 `git switch -c dev` 建立草稿分支再继续。
- 工作树有未提交改动：先 `git commit -m "wip: <一句话>"` 存档，再整理。

## 2. 整理会：按主题分类

逐条看 `git log` 的输出，把提交分成三类：

| 类别 | 判据 | 处置 |
| --- | --- | --- |
| **A 有价值的独立主题** | 说得清「这解决了什么/改了什么」，且与其它主题不纠缠 | 拆到主题分支（§3） |
| **B 同一主题的返工/演进** | 多个 wip 其实是同一件事的多次调整 | 合成**一条** commit（§4） |
| **C 没成型的实验** | 试了没成、或价值说不清 | 不挑，留在 dev；dev 最后整支删除 |

给每个 A/B 组起一个**现在才定**的分支名：`<type>/<kebab-case-主题>`（如
`fix/ui-cards`、`feat/mx-rebuild`）。名字来自分类结果，不是开分支前想好的。

**向用户报告分类结果**（A/B/C 各含哪些提交、拟用的分支名），经确认再动手。

## 3. 拆分支：cherry-pick（不是 rebase）

三个铁律：

1. **用 cherry-pick 搬提交**（挑指定的几个复制过去）；rebase 是搬整串，不是拆分工具。
2. **所有主题分支都从 `main` 开**，不要互相基于 —— 否则 GitHub 会把前序分支的提交算进后序 PR 的 diff。
3. **每个主题分支单独通过门禁**：拆出来必须能独立编译/测试；c3 与 c7 纠缠同一函数时，要么归入同一分支，要么先把依赖补进前序分支。

```bash
# 干净提交（信息已达标）→ 直接挑
git switch -c <type>/<topic> main
git cherry-pick <sha...>          # 按原顺序逐个列

# wip 提交 → 只搬内容不搬历史，重新写一条正经提交（§4）
git switch -c <type>/<topic> main
git cherry-pick --no-commit <sha...>
git commit                        # 用 .tmp/commit-msg.txt 流程写正式信息
```

## 4. 重写提交信息

wip 信息禁止原样带进主题分支。每条 commit 重写为：

- 标题 `type(scope): 中文描述`（Conventional Commits，scope 必填）；
- 正文写**为什么**与**验证方式**，不写「试了 A 又试了 B」的过程叙事；
- 同一主题的多次 wip 合成一条（`--no-commit` 连续搬运后一次提交）。

## 5. 顺序 PR 与合并

1. 主题分支按**依赖顺序**（被依赖的先合）逐个走
   `分支 → push → PR → CI 绿 → squash merge → 删分支`；
   **PR 与合并都必须先经用户确认**（全局规则「版本控制」第 3、4 条）。
2. 每合并一个，下一个先 `git rebase origin/main`（解冲突后再 push）。
   squash 后 main 上是新 SHA，rebase 时 git 通常按 patch-id 跳过重复；内容有出入会当冲突，需人工确认。
3. 全部合并后 `git branch -D dev`（它的历史已分散进各 PR）；
   dev 若有独立工作树，先 `git worktree remove` 再删分支。

## 6. 收尾清单

- [ ] 每个主题分支单独 `npm test`（或仓库等价门禁）通过
- [ ] 提交信息无 `wip:` 残留
- [ ] PR 按依赖顺序、逐个经用户确认
- [ ] dev 分支已删
- [ ] 探索期的结论（若有）已落 `docs/` 或渠道 `PROTOCOL.md` —— 探针脚本留 `.tmp/`，结论才是资产

## 7. 何时触发整理会

满足任一即停下探索、开始整理：

- dev 攒了 **8-10 个 commit**；
- 距上次整理 **数天**；
- 自己**说得清这批做了什么**的时刻（敏捷的最小可交付节奏）。
