# 模块注释约定（文件头 / 函数 docstring / 文档）

渠道包 `src/` 里的每个 `.ts` 模块都带一段文件头注释（Block Comment），用来回答「这个文件是做什么的、有什么关键约束」。
本约定把「什么该放在哪里」拆成三层，避免注释与 `docs/channels/<cid>/PROTOCOL.md` 出现双份事实源。

## 1. 三层分工

| 层 | 位置 | 职责 | 回答的问题 |
| --- | --- | --- | --- |
| 文档 | `docs/channels/<cid>/PROTOCOL.md` | 端点、字段、限制、实测结论、证据等级 | 「上游协议长什么样」 |
| 函数注释 | 被治理函数上方的 docstring | 影响该函数行为的 why（决策取舍） | 「为什么这样写」 |
| 文件头 | 模块最顶的 `/** … */` | 导航：一句话职责 + 关键约束 + 指引 | 「读这个文件前必须知道什么」 |

判断口诀：**what 去文档、why 跟函数、头部只做导航**。

- 协议事实（端点、字段、状态码、限制数）的唯一事实源是 `docs/channels/<cid>/PROTOCOL.md`。
  代码里出现同一事实的副本，协议一改就要改两处，漏一处就变成过时误导性注释（违反注释约定）。
- 设计决策的 why（比如「双轨缺一不可」「折叠成一条 user 文本」）附着在它被治理的函数 docstring 上。
  对一个函数的读者而言 why 就在眼前；对其它 why 不相关的函数，这段 why 不该出现在视野里。
- 文件头只留「不看这几行就完全读不懂本文件」的**行为级约束**；细节全部指针到 `PROTOCOL.md`。

## 2. 文件头模板（≤ 12 行）

```ts
/**
 * <一句话：模块职责>。
 *
 * 关键约束（端点/字段/实测见 docs/channels/<cid>/PROTOCOL.md）：
 *   - <只列「读懂本文件必需」的行为级约束，不超过 3 条>
 *
 * 铁律：<安全/红线类约束，一行>
 */
```

写入细则：

1. **头部不写日期、不写实验记录、不写「推翻了某结论」** —— 时间线属于 `PROTOCOL.md` 的证据等级体系。
2. **协议事实头部最多留 3 条**，且必须是「不读就完全看不懂本文件」级别（如「SSE 是累积帧需 suffix-diff」）；
   能查文档就知道的（如具体端点路径）删掉，靠一行指引指针到 `PROTOCOL.md`。
3. **why 跟着代码走**：一个结论治理哪几个函数，那段 why 就写在那些函数的 docstring 上；
   文件头只用一句话概括性提及（如「工具走双轨：toolConfigs + prompt 指令块」）并指向函数。
4. 不需要铁律的模块，删掉「铁律：」行。

## 3. 与仓库已有规则的关系

- 注释「写什么内容」（why 取舍、时效地雷、日期与署名判据）见 [CODE-COMMENTS.md](./CODE-COMMENTS.md)——
  本约定管「放哪一层」，它管「写什么」。
- 本约定是仓库注释规范「注释一律中文、简洁、不复述代码；随代码同步更新，禁止留过时注释」的具体落地。
- 渠道 PROTOCOL.md 才是协议事实的**唯一事实源** —— 本约定将「事实在文档、导航在头部」固化成模板，
  避免再出现「注释和文档同时声称同一事实」而导致的双源漂移。
- 文件头指引一律写相对路径 `docs/channels/<cid>/PROTOCOL.md`（工作区内跨包引用统一用仓库根相对路径）。
