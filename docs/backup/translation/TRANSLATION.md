# 请求上下文翻译（英译中）—— 已下线，方案留档

> **状态：功能已随请求日志的「上下文」弹窗一并移除（2026-11-07）。本文只作方案留档，
> 供以后别的项目或本仓新功能复用**，不是当前实现的文档。
>
> 下线原因：「翻译」按钮只服务上下文弹窗，弹窗移除后它没有入口。代码侧已删除
> `packages/ui/src/lib/translate.ts`、`packages/core/gateway/src/http/console/translate-proxy.ts`
> 与 `POST /web/api/translate` 端点。
>
> 可复用的部分（与弹窗无关、独立成立）：
> - **「大量英文」的判定算法**（§3）：英文功能词占比 + 字母脚本占比，不引 n-gram 语言库；
> - **分块与缓存策略**（§2）：按段落切块、逐块缓存、拼回原文；
> - **网关代发的取舍**（§2 末）：为什么不给浏览器直连公开端点 —— 跨域、端点暴露、
>   超时口径三件事都该收在一处；
> - **入参校验与上限**（§5）：条数 / 单条字符 / 单批总字符三层，配请求体上限与断流保护。

请求日志「上下文」弹窗里的正文（系统提示词 / 用户消息 / AI 回复 / 工具结果）经常整段是英文。
本功能在**判定为「大量英文」的正文右上角**（复制按钮左侧）加一个「翻译」按钮：点一次看中文，
再点回原文。译文只存在内存里，**绝不回写日志正文**。

设计参照 `dsh-skills-manager/docs/TRANSLATION.md`（同一套「公开翻译端点 + 网关代发 +
客户端分块缓存」的思路），但本项目**没有宿主 `translator` 服务可复用**，所以代发这一环
自己落在控制台 API 上。

## 1. 一句结论

翻译 = 把几段文本 POST 到一个**无密钥的公开端点**，把返回里的 `text` 取出来拼回去。
不调模型、不消耗额度、不占账号池。

实际链路：

```
上下文弹窗（浏览器） → POST /web/api/translate（本机控制台，同源）
                     → POST https://edge.microsoft.com/translate/translatetext
                     ← [{"translations":[{"text":"…"}]}] → 拼回正文
```

## 2. 分块与分层

| 层 | 位置 | 负责 | 不负责 |
|---|---|---|---|
| 浏览器 | `packages/ui/src/lib/translate.ts` | 判定「大量英文」、剥出代码块、切块、缓存、拼回 | 联网 |
| 控制台 API | `packages/core/gateway/src/http/console/console.ts`（`/api/translate` 路由） | 同源校验、请求体上限、错误码 | 切块、缓存 |
| 翻译代理 | `packages/core/gateway/src/http/console/translate-proxy.ts` | 入参校验（条数 / 单条 / 总字数）、超时、上游报文解析 | 语言判定 |
| 上游端点 | `edge.microsoft.com/translate/translatetext` | 实际翻译 | — |

为什么由网关代发而不是浏览器直连：跨域、端点暴露、超时口径三件事都不该摊在前端。
该端点**允许**跨域（实测 `Access-Control-Allow-Origin: *`），但仍然让网关发 ——
统一超时与单批上限只需要维护一处，前端只认 `code`。

## 3. 「大量英文」怎么判（算法选型）

判据是**英文功能词占比 + 字母脚本占比**，不用 `franc` / CLD3 这类 n-gram 语言识别。

为什么不用语言识别库：正文里混着代码、路径与 JSON，n-gram 模型会把 `[]{};` 密布的片段
判成法语 / 西语（实测 `franc(6.2.0)`：`function add(a,b){...}` → `fra`，
`{"model":...}` → `fra`，`这个函数返回 Promise…` → `deu`）。而我们要回答的不是
「这段是什么语言」，而是「这段是不是**英文散文**」。

四条判据（`shouldOfferTranslation()`）：

| 条件 | 阈值 | 排除什么 |
|---|---|---|
| 拉丁字母数 | ≥ 200 | `OK.` / 单个路径这种短片段 |
| 拉丁字母占比 | ≥ 60% | 中文为主的正文（原文能读，翻译添乱） |
| 汉字占比 | ≤ 20% | 中英混排但中文为主 |
| 功能词命中 | ≥ 15 次 或 ≥ 12% | 代码 / JSON / 工具名清单（英文字母多但没有散文结构） |

统计前先剥掉 ` ```…``` ` 围栏与 `` `…` `` 行内代码 —— 代码块里的「字母」不代表
这段正文的语言。只看前 30000 字符：MB 级正文全量扫一遍要几十毫秒，结论不会变。

功能词表是 closed-class words（the / of / and / to / is / that …），英文散文占比天然
12% 以上，代码与 JSON 几乎为 0。校准脚本 `.tmp/probe-english-detector.mjs` 用真实
payload 日志逐条打分，实测结果见 §7。

## 4. 分块策略

1. **按围栏切「散文 / 代码」段**（`splitCodeSegments`）：代码块整段原样保留，
   只翻散文。译文里贴代码是不能接受的。
2. **散文按空行切段，累计到 3000 字符一块**（`chunkProse`）：Markdown 的段落边界就是
   语义边界，在空行处切开，上游收到的仍是完整段落而不是被腰斩的半句。
3. **单段超长硬切**：优先句末（`。！？. ! ?`），其次空白，最后按字符数。
4. **整条消息上限 12000 字符**：再长就不是「读一段话」而是「翻一份文档」了；
   超出部分不翻，界面标注「只翻了前 X 字符」。

切块**不丢内容**：拼回来与原文只差空行规范化，单测直接断言这一点。

## 5. 服务端契约

`POST /web/api/translate`（同源校验，跨源一律 403）：

```jsonc
// 请求
{ "texts": ["第一块", "第二块"] }        // 1..12 条，单条 ≤ 4000 字符，合计 ≤ 40000

// 成功
{ "ok": true, "texts": ["译文一", "译文二"] }

// 失败（HTTP 400 / 502）
{ "ok": false, "code": "translate-text-limit", "error": "单条最多 4000 字符（实际 4001）" }
```

目标语言固定 `zh-Hans`：控制台界面语言恒定，放开 `to` 只是多一条被滥用的通路。

错误码（前端按 code 决定文案，不解析英文错误串）：

| code | 含义 |
|---|---|
| `translate-text-limit` | 条数 / 单条 / 总字数超限（**在发请求前就拒**） |
| `translate-request-failed` | 请求体形状不对，或网络层失败 |
| `translate-timeout` | 超过 20s |
| `translate-http-error` | 上游非 2xx（报文前 200 字符带回） |
| `translate-invalid-response` | 返回不是数组 / 条数不符 / 缺 `translations[0].text` |

### 5.1 上游实测边界（2026-11-05 直连）

| 场景 | 结果 |
|---|---|
| 单条 1000 / 3500 / 6000 / 8000 / 30000 字符 | 全部 200 |
| 一批 3 / 5 / 8 / 12 条（每条 3500 字符，合计 42000） | 全部 200，耗时 0.9–1.7s |
| 一批 20 条（合计 70000 字符） | **400** `Request exceeds the maximum allowed translation size.` |
| 一批 30 条（合计 105000） | **400** 同上 |

所以总字数上限取 40000（42000 实测通过，留余量）。前端每块 3000 字符、单条消息
最多 4 块，天然在这个范围内。

## 6. 前端行为

| 场景 | 行为 |
|---|---|
| 判定不通过 | **不出现**翻译按钮（不是禁用，是不渲染） |
| 首次点击 | 按钮变「翻译中…」（带 spinner），完成后变「原文」 |
| 再点一次 | 回到原文，按钮变「译文」 |
| 失败 | 按钮变红「翻译失败」，`aria-label` 带错误原因，再点即重试 |
| 译文展示中 | 正文下方一行小字「机器翻译 · 点「原文」看原样正文」 |
| 缓存 | 模块级 `Map`（key = 目标语言 + 原文），上限 40 条，刷新即失效 |

失败**整体回退原文**，不做部分混排：一段译好一段失败时若混排，读者无法判断哪半可信。

只翻**字符串正文**。数组形态（多模态 parts）与工具结果不做逐段翻译 —— 它们的结构差异
太大，逐段翻会把图文重排，收益远小于风险。

## 7. 判定阈值校准（实测）

`.tmp/probe-english-detector.mjs` 对真实 payload（2026-11-05 抓取）逐条打分，25 条样本：

| 正文 | 拉丁占比 | 汉字占比 | 功能词命中率 | 判定 |
|---|---|---|---|---|
| ZCode 系统提示词（4803 字符） | 1.00 | 0.00 | 0.29 | 翻译 |
| 会话摘要（15276 字符，中英混排） | 0.39 | 0.61 | 0.08 | 不翻 |
| `<system-reminder>` 技能清单（14242 字符） | 1.00 | 0.00 | 0.08 | 翻译 |
| 代码片段（3116 字符，`255 const cur = …`） | 0.95 | 0.05 | 0.04 | 不翻 |
| HTML 片段（1980 字符） | 0.92 | 0.08 | 0.00 | 不翻 |
| 中文说明（5449 字符） | 0.26 | 0.74 | 0.04 | 不翻 |
| 「The file … was read」短提示（214 字符） | 1.00 | 0.00 | 0.25 | 不翻（拉丁 < 200） |

关键区分：**技能清单与英文散文**都能过（它们是给人读的长英文），
**代码 / JSON / HTML / 中文** 都被拦住。

## 8. 已知边界

| 边界 | 说明 |
|---|---|
| 只翻字符串正文 | 多模态 parts、工具结果、reasoning_content 不翻 |
| 单条 12000 字符上限 | 超长正文只翻开头，界面标注 |
| 译文不落盘 | 刷新即失效；不写回日志（正文是排查事实源） |
| 无术语表 | 专有名词按上游通用译法（`Harness` 会译成「马具」这类），不干预 |
| 演示模式不支持 | 静态 Pages 没有网关，翻译按钮点下去报「演示模式不支持翻译」 |
| 质量取决于公开端点 | 长句偶有生硬；这是免密钥通道的代价 |

## 10. 复制按钮的取舍

弹窗顶部**没有**全局「复制全部内容」按钮：正文是**分片懒加载**的（元数据查询只回
元数据，不回正文），顶部按钮拼不出完整内容 —— 全局聚合与逐条复制二选一时，
逐条「复制完整 JSON」更可靠。

每条记录头部的复制按钮是「复制完整 JSON」：正文已全部加载就直接复制，还有剩余就先按
`total` 一次取全再复制（复制是显式动作，多等一下可以接受），读取期间显示 spinner。
