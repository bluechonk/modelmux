# 按账号账单与额度耗尽自动换号（`modelmux`）

本文件是**设计 + 实施说明**：为什么账单要按账号看、什么条件下自动换号、换号时守哪些边界。
实施已收敛进代码：决策在 `packages/core/gateway/src/pool/account-rotate.ts`，
重试编排在 `packages/core/gateway/src/http/chat/relay.ts`，
CLI 出口在 `packages/core/gateway/src/app/lifecycle/daemon.ts`。
规则层的权威描述见 [POOL-ARCHITECTURE.md](./POOL-ARCHITECTURE.md) §2.4 与 §3.3。

## 1. 为什么额度必须按账号看

额度是**账号级**的，不是渠道级的：

| 事实 | 观测（2026-10-28 实测 loomy） |
|---|---|
| 每个账号各有自己的每日赠送 | 4 个账号各自 `每日 5000 / 5000`，互不共享 |
| 每个账号各有自己的一次性新手奖励 | 每个账号各自 10,000 积分（`onboarding/tasks`） |
| 生效账号 ≠ 池里唯一账号 | 池里 3 个账号各有额度，但只有一个在服务 |

因此「渠道还剩多少额度」这句话本身是不完整的 —— 它只描述**当前生效的那个账号**。
`mx bill loomy` 原本只查生效账号，池里另外两个账号有多少额度只能去 Web 账号池页看。
按账号查询的**能力早就有**（`pool/pool-usage.ts::refreshAccountCredits` 每 3 分钟
逐个账号查一次并写进账本 `accounts[key].credits`，Web 账号卡片看的就是它），
缺的是 **CLI 出口**。

## 2. `mx bill` 的按账号输出

```
mx bill [<cid>] [--accounts]
```

单一渠道的输出形状（示例值）：

```
额度: 剩余 15547 / 15547 积分（已用 0，剩余 100%）
  · 永久积分: 15000/15000
  · 每日赠送: 547/547

账号（3）：
  * 00ddbce1…  131****6402  剩余 20000 / 20000 积分（100%）  生效中
    bb9732a0…  131****8010  剩余 1133 / 11000 积分（10%）
    77877118…  177****3009  剩余 14974 / 14974 积分（100%）
```

规则：

1. **池内 ≥2 个账号时默认列出**账号表（这是最容易被误解的场景）；单账号池不列，
   因为渠道级那行说的就是它。`--accounts` 可强制列出（含单账号）。
2. 账号表是**实时查询**（每个账号一次上游只读额度查询），不是账本缓存 ——
   用户敲 `mx bill` 就是要当下的数字。冷却中的账号照查（显式请求的语义优先），
   查询失败的那行如实打印失败原因，不影响其它行。
3. 账号行首字符 `*` 标出生效账号；`label` 取账号池的展示名（脱敏手机号 / 昵称），
   取不到退化成 key 前 8 位 —— 与 `mx acct <cid> list` 同一口径。
4. `--json` 增加 `accounts[]`：`{ key, label, active, ok, remain, size, used, unit, remain_percent, error? }`。
5. 全部渠道形态（`mx bill`）逐渠道打印渠道级那一行；加 `--accounts` 时逐渠道再列账号表。

## 3. 额度耗尽 → 自动换号

### 3.1 触发的判据（两步，先本地后联网）

一次请求失败后（失败错误码属于「可能是额度问题」的那一类，见 §3.4）：

1. **读最近一次账单**（本地账本 `pool-usage.json` 的 `accounts[active].credits.remain`，
   零网络开销）：
   - `≥ 100`（`LOW_CREDIT_THRESHOLD`）→ **不换号**：还有额度，说明是别的问题，
     交给既有的熔断/报错链路；
   - `< 100` 或**从未查过**（`null`）→ 进下一步。
2. **立刻重查一次 bill**（`fetchCredits({ refreshOn401: false, credential })`，用该账号自己的凭据）：
   - 查询失败 → **不换号**（无法判定，不拿猜的结论去换账号）；
   - `≥ 100` → **不换号**（刚查过还有额度，不是额度问题）；
   - `< 100` → **确认额度耗尽**，进 §3.2。

> 「先读缓存、再联网核实」这条两段式是刻意的：上游一抖动就换账号会让请求在用户不知情时
> 落到另一个账号上（额度、配额、IP 风控各算一份），排障时也看不出究竟谁在服务。
> 只有**两次证据都指向额度不足**才动账号。

### 3.2 换号动作

1. 把**生效账号**标 `cooldown`（不是 `error`）—— 额度不足不是故障，窗口刷新会自己好；
   截止时间取渠道声明的 `billing.quotaPeriod().resets_at`，渠道没声明就兜底次日本地 0 点。
   理由文案带实测数字（`额度不足（账单 0 < 100），已自动换号`），直接进 Web 卡片与日志。
2. 从池里挑替代账号，**排除**：
   - 正在 `cooldown` 的（额度没刷新，换过去一样失败，而且 `activateAccount`
     会顺手清掉 `cooldown_until` —— 等于假装它有额度，必须挡在前面）；
   - `unauthorized` 的（凭据失效，重试永远无效）。
3. 排序：已知额度**降序** → 未知额度 → 已知低额度。取第一个。
4. `activateAccount(key)` 切生效账号（复制池内凭据回 `credentials.json`），
   本次请求用新账号**重试一次**。

没有可选替代账号 → 不换号，如实回错误（池子全空/全冷却时不要假装能救）。

### 3.3 什么情况绝对不换号

| 情形 | 为什么 |
|---|---|
| 鉴权失败（`not_authenticated` / `upstream_unauthenticated`） | 换账号会把「凭据被撤销」这个真问题掩盖成随机成功；既有设计明确要求**只刷新 token 重试本账号**，失败如实报错让用户重登 |
| 客户端已经收到字节（`res.headersSent`） | 响应头已发出，再开一条上游流就是**两个响应**（内容重复/串台） |
| 免费模型撞余额错误（`upstream_insufficient_quota`） | 倍率 0 的模型不吃额度，这条错误与账号额度无关；且免费模型路径刻意不写账号状态 |
| 一次请求已经换过一次 | 防循环：换号成功走新账号，失败就如实报错，不要在同一条请求里轮着试 |

### 3.4 可触发换号的错误码

`quota_exhausted`（冷却短路 / 上游额度错误体）、`upstream_error`、`upstream_timeout`。
后两个是「可能是额度问题的通用失败」：有些上游额度烧光后不回标准额度错误，
而回 5xx 或干脆断流 —— 这类只有账单能证伪，所以它们**也**要先读账单再决定（§3.1 的两段式保证了
「有额度就不换」）。

## 4. 与既有机制的分工

| 机制 | 触发 | 动作 | 恢复 |
|---|---|---|---|
| 连败熔断（`error` + `trip_until`） | 连续瞬时失败 3 次 | 短路该账号，指数退避半开试探 | 自动（试探成功恢复） |
| 额度冷却（`cooldown`） | 上游额度错误体 / 账单查到 0 | 短路**付费**模型，免费模型照常 | 自动（窗口刷新） |
| **额度耗尽自动换号（本文件）** | 请求失败 **且** 账单两次都 < 100 | 旧账号标冷却 + 切到有额度的账号 + 本次请求重试一次 | 换号后立刻生效；旧账号等窗口刷新 |

三者不重叠：熔断管「账号坏了」，冷却管「这个账号没钱了先别用它」，
自动换号管「池里还有别的账号，别让用户看到 503」。

## 5. 边界与风险

1. **多账号是同一个人的账号**（都是主人自己扫码入的池）—— 自动换号不涉及跨用户凭据，
   与「伪造身份」无关。
2. **额度快照可能是旧值**：账单派生冷却已有 30 分钟上限（`BILLING_COOLDOWN_PROBE_MS`），
   本机制同源：换号后旧账号最多冷却到窗口刷新或 30 分钟（探测上限），到期会重查，
   查到有额度即恢复。
3. **`mx bill` 的账号表会在上游留下 N 次只读查询**：与 3 分钟一次的后台刷新同源同量，
   不引入新的查询节奏；池子很大时可用 `--json` 自行裁剪。
