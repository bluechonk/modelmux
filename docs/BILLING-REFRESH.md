# 额度刷新与估算余额

账号池的后台额度查询按**账号档位**调度，不是全池固定周期轮询。本文是这条调度的唯一事实源；
选路与账号生命周期见 [POOL-ARCHITECTURE.md](./POOL-ARCHITECTURE.md)。

## 1. 目标与非目标

目标：

- 正在使用的账号额度能在一分钟内反映到控制台；
- 空闲账号仍保持分钟级新鲜度，但不为它支付全速查询成本；
- 同一渠道内多个账号不落在同一毫秒，避免被上游认成批量探测；
- 被上游限流时自动退避，而不是按固定节奏把封锁拖长。

非目标：

- 不用估算值参与选路（选路只认真实账单值）；
- 不为 `unauthorized` / 熔断账号重试额度查询（重试永远失败）；
- 不追求「每轮刷新全部渠道」——手动 `mx model usage --refresh` 仍提供全量语义。

## 2. 档位与间隔

判据只有两个：账号健康态、最近一次**成功转发**时刻（`billingTierOf`，纯函数）。

| 档位 | 进入条件 | 刷新间隔 |
| --- | --- | --- |
| `active` | 最近 `ACTIVE_WINDOW_MS`（5 分钟）内成功转发过 | `ACTIVE_REFRESH_MS` = 1 分钟 |
| `idle` | 其余可用账号（含从未成功转发过的） | `IDLE_REFRESH_MS` = 3 分钟 |
| `paused` | `unauthorized` / `error`（熔断）/ 额度冷却未到期 | 不查 |

失败请求不更新活跃判据：失败不代表账号在被正常使用，把它升到 1 分钟只会更频繁地打上游。

档位每轮重算，不需要持久化的「当前档位」状态；账号恢复使用后自然升回 `active`。
算出的档位写进账本 `billing_tier` 仅供展示与排障。

## 3. 调度循环

调度器每 `SCHEDULER_TICK_MS`（15 秒）跑一轮 `runScheduledRefresh`。tick 不联网，
只比较账本里的 `billing_at` 与档位间隔（`isBillingDue`）。

```text
tick ──► 渠道可用？ ──否──► 跳过
           │是
           ▼
     渠道级 429 退避中？ ──是──► 跳过整个渠道
           │否
           ▼
     逐账号算档位 ──► paused / 未到期 ──► 跳过
           │到期
           ▼
     按错峰延迟逐个查询 ──► 成功写额度；429 记连击
```

渠道级条目用**生效账号**这一轮的实测值回写，不再额外发一次渠道级查询。

同一时刻只允许一轮调度：单轮可能因错峰与慢端点超过 tick 间隔，重叠执行会对同一批账号
重复查询；手动全量刷新在跑时调度也让路。

`MODELMUX_BILLING_REFRESH_MS` 覆盖 tick 间隔；设为 0 关闭后台刷新。

**启动抖动**：首个 tick 延迟 `0..tick` 的随机时长。否则网关重启时所有账号的
`billing_at` 同时过期，会在同一轮全部开火。

`BILLING_TTL_MS`（8 小时）是另一条判据，只服务聊天请求路径的「顺手补一次」
（`maybeRefreshBilling`），与后台调度互相独立。

## 4. 错峰

同一渠道内本轮到期的账号按 `staggerDelayMs(index, count, jitter)` 排定发送时刻，
全部落在 `STAGGER_WINDOW_MS`（1 秒）窗口内。

- 槽位 = 1 秒 / 本轮账号数，账号按序号占用自己的槽；
- 槽内加随机抖动，避免两个账号撞在同一毫秒；
- 顺序稳定：同一账号每轮的相位基本固定，看起来像独立客户端，也便于复现排障。

纯随机每轮重排会让上游看到「同一秒内 N 个账号各自查询」，稳定相位加抖动更接近
真实的多客户端形态。

## 5. 429 退避

额度查询是最容易被限流的端点（codebuddycn / workbuddy 实测回过 `HTTP 429`）。
把 429 当普通失败、按 1 分钟重试只会把封锁拖长。

| 事件 | 结果 |
| --- | --- |
| 单次 429 | 渠道连击 +1，不立刻退避 |
| 连击达到 `RATE_LIMIT_STREAK_LIMIT`（2） | 渠道退避 `RATE_LIMIT_BACKOFF_MS`（10 分钟） |
| 任意一次成功 | 连击与退避清零 |

退避期内整个渠道不查额度（`inRateLimitBackoff`）。退避状态写在渠道账本条目
`billing_429_streak` / `billing_backoff_until`。

## 6. 签到后的空窗

签到领取会实测并写回该账号额度，`billing_at` 随之前移。下一轮按到期判定自然跳过，
不需要额外的「签到后 N 分钟不查」状态。

## 7. 按 usage 估算余额

部分渠道在每轮对话的 `usage` 里直接给出本次消耗。渠道通过
`upstream.consumedCredits(usage)` 上报，共享层按账号累加到账本 `spent`。

| 渠道 | 字段 | 单位 |
| --- | --- | --- |
| loomy | `usage.points_consumed` | 积分 |
| workbuddy | `usage.credit` | credits |
| codebuddycn | `usage.credit` | credits |
| traecn | 无 | 只有 token 用量，不参与扣减 |
| raccoon | 未测得可用字段 | 不参与扣减 |

展示口径：

- 估算余额 = 上次账单 `remain` − 累计 `spent`，控制台标「估算」；
- 流式在每帧 usage 上记，非流式在聚合完成后记一次（两条转发路径都要接）；
- 只在 `spent.unit` 与 `credits.unit` 一致时扣减，量纲不同不混加；
- 请求内把上游报的值当**累计量**，只记增量：同一帧重复出现不会重复扣；
- 下次账单查询成功即清零（真实值已覆盖增量）；
- **不参与选路**，路由仍用真实账单值。

`usage.quota.percent` 是剩余百分比而非绝对余额，不作为消耗增量。

## 8. 可观测性

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `billing_tier` | 账号账本条目 | 本轮算出的档位 |
| `last_ok_at` | 账号账本条目 | 最近成功转发时刻（活跃判据） |
| `spent` | 账号账本条目 | 上次账单后的累计消耗增量 |
| `billing_429_streak` / `billing_backoff_until` | 渠道账本条目 | 限流连击与退避截止 |
| `estimated_remain` / `tier` | 控制台 billing 行 | 估算余额与档位 |

控制台账号详情显示「额度刷新：活跃 · 1 分钟 / 空闲 · 3 分钟 / 暂停」。

## 9. 验收与未验证项

已覆盖（单测，零网络）：

- 档位判据、到期判定、错峰延迟、429 连击与退避、消耗累加与估算余额；
- `runScheduledRefresh` 的「只查到期账号」「渠道级回写」「退避期内不查」
  「多账号错峰」；
- `noteFrameUsage` → 渠道钩子 → 账本估算余额的完整接线。

未验证：

- 各上游对 1 分钟节奏的真实容忍度（限流阈值未知，只能靠 429 退避兜底）；
- workbuddy / codebuddycn 的 `credit` 在长对话中的累计精度（小样本实测为 0，
  需要真实长会话对账）；
- raccoon 的消耗字段（重登后仍未见可用字段）。
