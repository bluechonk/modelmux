# 代码注释内容规范（写什么 / 不写什么 / 日期与署名）

全局规则「代码注释一律中文、简洁、不复述代码」的内容层细则，全仓 `.ts` 通用。
渠道模块的文件头 / docstring / 文档**三层分工与模板**见 [MODULE-COMMENTS.md](./MODULE-COMMENTS.md)——
那边管「放哪一层」，本文件管「写什么内容」。

## 1. 原则：写 why 不写 what；注释要「常青」

1. 注释回答「代码为什么这样写」，不回答「做了什么」——what 代码自己表达；
   协议事实的 what 的唯一事实源在 `docs/channels/<cid>/PROTOCOL.md`（三层分工见 MODULE-COMMENTS.md §1）。
2. 注释应当「常青」：读起来像今天写的，与代码同生同灭。凡会随时间腐烂成谎言的内容
   （修订记录、手工维护的时间戳、署名）一律不进注释——git log / git blame 是修改历史的唯一事实源。

## 2. 该写的三类

| 类型 | 回答的问题 | 例 |
| --- | --- | --- |
| 决策取舍 | 为什么是 A 不是 B | 「只等 120s：实测排队能拖到 290s，客户端早已放弃」 |
| 约束前提 | 代码形态看不出来的外部约束 | 「上游对空 shell 不带 tool_calls，不影响工具配对」 |
| 时效地雷 | 依赖上游「当前行为」的结论何时会失效 | 「实测（2026-10-25）排队能拖到 290s；上游改排队机制后需重测」 |

时效标注（地雷例外）：**日期绑在事实上，不绑在人身上**。逆向型项目上游行为会漂，
实测时点是判断结论新鲜度的唯一依据——这类日期有信息量，必须写；它不是「修订日期」，
写的是「事实在何时成立」，不是「代码在何时修改」。

## 3. 不写的四类

| 禁写 | 理由 | 归宿 |
| --- | --- | --- |
| 修订记录（「改于 X 日」「第几版」「本次修改了什么」） | 手写日期注定漂移成过时注释；git log 是唯一事实源 | 提交信息 + git log |
| 作者署名 / 审批留痕（「主人 2026-10-25 定」） | 谁拍板 `git blame` 一眼可见，对读者无信息量；该写的是「为什么定这个值」 | git blame |
| 复述代码、半吊子翻译 | 注释与代码双份事实源，代码一改注释先变谎言；专有名词保持英文原文 | —— |
| 注释掉的代码 | 死代码无人维护，必成误导 | 直接删，git 历史兜底；动机写进提交信息 |

文件头禁写日期与实验记录是 [MODULE-COMMENTS.md](./MODULE-COMMENTS.md) §2 的既有条款，不在此重复。

## 4. 反例 → 正例

反（审批留痕，日期绑人）：

```ts
// 取 120 秒（主人 2026-10-25 定）：比容忍更久没有意义。
```

正（事实 + 时点 + 取舍）：

```ts
// 只等 120s：实测（2026-10-25）qoder 排队能拖到 290s，客户端早已放弃，
// 干等不如切「劝换渠道」；上游改排队机制后需重测。
```

## 5. TODO / FIXME

1. 格式统一可检索：`// TODO(<名字>): 待办描述` / `// FIXME(<名字>): 缺陷描述`。
2. 带清理条件（何时可删），不带修订日期。
3. 定期清理：被遗忘的标记迟早变成误导。

## 6. 与既有规则的关系

- 全局 `~/.zcode/AGENTS.md`「代码与注释」：中文、简洁、不复述、随代码同步更新——本文件是其内容层细则。
- [MODULE-COMMENTS.md](./MODULE-COMMENTS.md)：文件头 / docstring / 文档的三层分工——本文件管「写什么」，它管「放哪里」。
- 时间线与实测证据（何时测的、原始报文）落 `docs/channels/<cid>/PROTOCOL.md` 的证据等级体系，不落注释。
