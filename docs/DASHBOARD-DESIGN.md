# 仪表盘设计方案（/web/ 首页 · 运行视图）

> 状态：**P0 / P1 已完成，P2 待实施**，2026-10-28 拟定 / P0 P1 同日完工。
> 本文只描述「模块与布局该长成什么样、为什么这样设计、边界在哪里」；实现细节与既有约束以
> [WEB-CONSOLE.md](./WEB-CONSOLE.md) 为契约，本文实施后把「现状」收敛进该文档。
> 数据口径与日志字段引用 [LOGGING.md](./LOGGING.md)。

## 0. 结论（TL;DR）

现状仪表盘只有「配置态」信息——接入端点、模型数、渠道数、端点数——没有任何
「运行态」信息：今天跑了多少请求、成功多少、慢不慢、烧了多少 token、各渠道还健康不健康，
首页一律看不到。而这台网关最大的价值恰恰是「它是活着的、用得怎么样」。

方案一句话：**接入盒保持在首屏不动，「一行静态统计」升级成「运行视图」**：

1. **KPI 行**（运行时四格）：今日请求（含成功率）/ 今日失败（含慢请求）/ 平均耗时 / 今日 tokens；
2. **渠道状态卡**：每渠道一行，账号健康分布 + 今日成败计数，整行可点进账号池；
3. **模型池概览卡**：模型总数 / 免费 / 可吃图 / 支持思考，一键去 `/models`；
4. **最近请求卡**：最近 5 条（时间 / 模型 / 结果 / 耗时），失败可点击进入日志页；
5. **网关控制面板**：保留运行态 + 播放/暂停/重启，从通栏收敛为右栏 1/3。

数据走一个新轻量聚合端点 `GET /web/api/overview`（一次拉全、5 秒轮询），不新增依赖、不引图表库。

## 1. 现状与问题

### 1.1 当前仪表盘（已落地部分）

| 区块 | 内容 | 类型 |
| --- | --- | --- |
| 接入盒 | base_url / chat_url / endpoints，逐行可复制 | 配置（高频） |
| 统计行 | 网关状态 / 可用模型 / 供给渠道 / 接入端点 + 刷新 | 配置（静态计数） |
| 网关控制 | 播放（禁用）/ 暂停 / 重启 + 恢复说明 | 状态 + 操作 |
| 模型列表 | 已拆为独立 `/models` 页（本方案以后无首页级模型表） | 已落地 |

### 1.2 问题清单（按严重程度）

1. **运行态完全不可见**：首页无法回答「这台网关现在怎么样」——请求量、成功率、失败数、
   慢请求数、token 消耗、账号健康，全部要去各子页才能看。
2. **渠道健康在首页缺席**：账号是否熔断（`error`）、是否冷却（`cooldown`）、是否未登录，
   只有 `/accounts` 才有；而首页才是「扫一眼」的位置。
3. **失败无感知**：网关今日失败多少次、是不是某渠道正在连败，首页零提示。
4. **布局权重倒挂**：最静态的 base_url 占据首屏最大一块，运行状态被推到下面。
5. **统计行口径不统一**：「可用模型」计数口径与 `/models` 页不保证一致，且没有单位与时间维度。

## 2. 设计目标与边界

### 2.1 目标

1. **一屏回答「活着吗、好不好用、用了多少」**：KPI 数字与渠道健康在首屏（1440×900
   不滚动即见主体）；接入盒仍在最顶，不因改造让高频操作下移。
2. **仪表盘做摘要和导航，详情永远在对应子页**：管理动作（登录 / 切号 / 删号）不进首页；
   模型清单、日志明细、账号明细各自的页面保持权威。
3. **零新增运行时依赖**：不引图表库、不引状态库；数字用现有令牌与 CSS 表达。
4. **口径与详情页完全一致**：`outcome` 三桶、tokens 单位（百万 M / 亿），与
   [LOGGING.md](./LOGGING.md) §3 对齐，不出现「首页一个口径、日志页另一个」。
5. **演示模式 1:1**：`demo.ts` 同步提供 overview 数据，Pages 演示继续完整可用。

### 2.2 边界（明确不做，防方案膨胀）

- **不做历史趋势图**：日志按天轮转、无长期保留（见 LOGGING.md §6），跨天聚合没有数据源；
  「今日」是唯一有意义的时间窗。
- **不引图表库**：KPI 是数字不是图。
- **不做推送与告警**：本机工具，人就在机器前。
- **不做负载 / QPS / 并发指标**：本地网关串行转发，无并发维度。
- **不把管理动作搬进首页**：网关启停是唯一例外（已落地）。

## 3. 总体布局与规则

### 3.0 布局规则（全站统一，仪表盘也遵循）

- **固定**：页面在允许纵向滚动时不滚动；需要滚动的内容（如日志表）只在自己的容器里滚。
  仪表盘首屏密度高，默认不整页滚动——除非 KPI 与卡片超出视口，才整页滚动。
- **间距**：卡片间 `gap-3`，卡片内 `p-4`；标题用 `panel-title`。
- **状态语义**：成功 = `--free`，失败 = `--danger`，中断 = `--warn`，未知 = `ink-faint`；
  棘轮不做额外配色。
- **表意图形**：每卡头部带 lucide 图标（与导航同族），统一 16px。
- **可触达**：可点击的行用 `<button>`/`<tr>` 包裹整行；键盘可达（`focus-visible`），
  hover 不用来承载信息（铁律见 WEB-CONSOLE「交互铁律」）。

### 3.1 桌面骨架（≥ 1024px，12 栅格）

```
┌──────────────────────────────────────────────────────────────────────┐
│ ① 接入盒（全宽，KPI 之下仍可滚过）                                    │
│   base_url / chat_url / endpoints（复制）                            │
├──────────────────────────────────────────────────────────────────────┤
│ ② KPI 行（全宽）： 请求·成功率 / 失败·其中慢 / 平均耗时 / 今日 tokens │
├────────────────────────────────────────┬─────────────────────────────┤
│ ③ 渠道状态（col-span-8）               │ ④ 模型池概览（col-span-4）    │
│  每渠道一行 + 账号健康分布 + 成功/失败  │  总数/免费/可吃图/支持思考    │
│                                        │「查看全部模型 →」            │
├────────────────────────────────────────┼─────────────────────────────┤
│ ⑤ 最近请求（col-span-8）               │ ⑥ 网关控制（col-span-4）     │
│  最近 5 条：时间·模型·结果·耗时        │ 运行/暂停/重启 + 恢复说明     │
└────────────────────────────────────────┴─────────────────────────────┘
```

### 3.2 断点降级

| 断点 | 行为 |
| --- | --- |
| ≥ 1024px（lg） | 双列：8+4 |
| 640–1023px（md） | 收敛为单列，顺序：KPI → 渠道状态 → 模型池 → 最近请求 → 网关控制 |
| < 640px（sm） | KPI 2×2；渠道行只保留 cid + 状态点 + 成功/失败；模型池只保留总数一行；接入盒只留 base_url（沿用既有 hidden 逻辑） |

### 3.3 布局取舍

- **KPI 在接入盒下方而不是替代**：接入盒是「把 base_url 抄走」的最高频操作，KPI 是「扫一眼」。
- **渠道状态占左侧大列**：渠道是这台机器的主体资产，信息密度最高。
- **最近请求放第三行**：回答「刚才发生了什么」，与渠道 / 模型池一起构成第一屏主体。
- **网关控制收窄**：功能不变，从通栏卡片（≈200px 高）收敛为右栏竖卡。

## 4. 数据通道设计

新增轻量聚合端点 `GET /web/api/overview`，**无参数**；可带 `?refresh=1` 供手动刷新。

```jsonc
{
  "ok": true,
  "date": "2026-10-28",
  "gateway": { "ui_state": "running", "gateway_error": "" },
  "usage": {
    "requests": 1234, "success": 1200, "failure": 30, "other": 4,
    "slow": 8,                          // 慢阈值同 LOGGING
    "avg_duration_ms": 3200,            // null = 无样本
    "tokens": { "prompt": 12345678, "completion": 890123 }  // 原始数，前端换算单位
  },
  "channels": [
    { "cid": "catpaw", "models": 30,
      "statuses": { "ok": 2, "cooldown": 0, "error": 0, "unauthenticated": 0 },
      "requests": { "success": 900, "failure": 4 } }
  ],
  "model_pool": { "total": 0, "free": 0, "vision": 0, "thinking": 0 },
  "recent": [
    { "id": "…", "ts": "…", "cid": "a", "model": "glm-…", "outcome": "success", "status": 200, "duration_ms": 1234 }
  ]
}
```

### 口径与实现约定

- 计数按当天；`avg_duration_ms` 无样本返回 `null`；tokens 缺失不计 0。
- 账号健康来自内存快照，不触发任何真实重查（那是 /accounts 的职责）。
- 实现时应同步在服务端做一次「扫描你说的窗口，但把超窗标记 `truncated` 带出战局」，
  以日志页/LOGGING.md 的美均为准。

## 6. 决策记录（为什么这样设计）

1. **KPI 为什么是这四个**：请求量（运载）、失败（健康）、平均耗时（体验）、tokens（成本）——
   看完就知道「好不好用」；模型数与渠道数是配置态，属于 /models 与 /accounts。
2. **为什么新增 /overview 而不是前端组合请求**：一次 fetch 完成整个页面，免去多请求协调；
   后端内存里按日扫一遍，规模与当前 `/logs` 读窗口一致（都是扫描当日记录）。
3. **为什么渠道卡整行可点而不做「详情」按钮**：数据没有可钻取层级，整行跳转更直接。
4. **网关控制为什么保持原功能不变**：暂停 / 重启行为已确认过；不动它以免引入回归。
5. **不做实时图表**：日志按天轮转，跨天聚合无数据源，等有历史再说。
